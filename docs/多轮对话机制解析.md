# 多轮对话机制解析

## 一、整体架构

```
用户提问 → 问题增强(LLM/规则) → 上下文需求分析 → 上下文提取 → 构建 context prompt → SQL 生成
                ↑                        ↑                    ↑
           历史问题(上一轮)           指代词/追问检测         entity_ref, time_range, history_sql...
```

**核心数据流**：
- `generate_sql_logs`：当前 chat 下所有「生成 SQL」步骤的 ChatLog 列表（按时间排序）
- `latest_log = generate_sql_logs[-1]`：最近一轮的 SQL 日志
- `latest_log.pid` → `ChatRecord`：关联的对话记录（含 question、sql、data）
- `latest_log.messages`：该轮的人机消息（human 为历史问题）

---

## 二、主要模块与职责

### 1. 问题增强（Question Enhancement）

**位置**：`context_manager.enhance_question_with_history()` → `QuestionEnhancer.enhance_question()`

**流程**：
1. 优先调用 `_enhance_question_by_llm()`（LLM 智能补充）
2. 若 LLM 无结果，则用规则增强

**规则增强类型**（`question_enhancer.py`）：

| 类型 | 检测函数 | 示例 | 增强逻辑 |
|------|----------|------|----------|
| 时间追问 | `is_time_follow_up()` | 「2024年的呢？」 | 用 2024 替换历史问题中的年份 |
| 地区追问 | `is_region_follow_up()` | 「广东的呢？」 | 用广东替换历史问题中的地区 |
| 公司主体追问 | `is_company_follow_up()` | 「集团的呢？」 | 用集团替换历史问题中的主体 |
| 指标追问 | `is_metric_follow_up()` | 「营业收入呢？」 | 用营业收入替换历史问题中的指标 |
| 指代词 | 含「这些」「它们」「上述」等 | 「这些公司营收多少？」 | 在指代词前插入历史问题中的时间/地区等 |

**约束**：追问句式长度 ≤ 25 字符（`_FOLLOW_UP_MAX_LEN`），超过则视为完整问句，不按追问处理。

---

### 2. 上下文需求分析（Context Needs Analysis）

**位置**：`ContextStateManager.analyze_context_needs()`

**触发条件**：`generate_sql_logs` 非空

**分析逻辑**：

| 条件 | 设置的 needs |
|------|--------------|
| 含指代词（这些/它们/上述/刚才...） | `needs_entity_ref`, `needs_intent_context`, `needs_terminology_enhancement` |
| `is_any_follow_up()` 为真 | 同上 |
| 含「类似」「参考」「按照」 | `needs_sql_pattern` |
| 含「继续」「接着」「然后」 | `needs_intent_context` |
| 有历史日志 | `needs_intent_context` |
| 当前问题无时间词 且 历史有时间 | `needs_terminology_enhancement`（用于时间延续） |

**entity_types**：根据当前问题中的「公司」「城市」「省」「时间」等词推断需要的实体类型。

---

### 3. 上下文提取（Context Extraction）

**位置**：`ContextStateManager.extract_context()`

**数据来源**：`latest_log.pid` → `ChatRecord`（含 `data`、`sql`）

**提取内容**：

| 类型 | 条件 | 提取器 | 输出 |
|------|------|--------|------|
| 实体引用 | `needs_entity_ref` | `EntityReferenceExtractor` | `entity_references`（公司/城市/省份列表） |
| SQL 模式 | `needs_sql_pattern` | `SQLPatternExtractor` | `sql_pattern`（占位符形式） |
| 时间范围 | 总是尝试 | `extract_time_range()` | `time_range`（start/end 或 time） |
| 历史 SQL | `needs_terminology_enhancement` 或 `needs_intent_context` | 直接取 | `history_sql`（截断至约 500 字符） |

**时间范围提取**（`extractors.extract_time_range`）支持：
- `BETWEEN 'YYYYMM' AND 'YYYYMM'`
- `BETWEEN 'YYYYMMDD' AND 'YYYYMMDD'`
- `= 'YYYYMM'` / `IN ('YYYYMM', ...)`
- **不支持**：`create_date LIKE '2026-02%'` 这类 LIKE 模式

---

### 4. 上下文提示构建（Context Prompt Builder）

**位置**：`ContextPromptBuilder.build()` → 注入 `<context>...</context>`

**格式**：
```xml
<entity-ref type="company">公司A, 公司B, ...</entity-ref>
<entity-ref type="city">城市1, 城市2</entity-ref>
<sql-pattern>SELECT {fields} FROM {table} WHERE ...</sql-pattern>
<intent>延续上一轮查询，新增营业收入维度</intent>
<time-range start="202501" end="202512">202501 至 202512</time-range>
<history-sql>SELECT ... FROM ... WHERE ...</history-sql>
```

**意图分析**（`IntentContinuityAnalyzer`）：仅在 `history_question` 存在且当前问题含指代词时分析，用于生成 `<intent>`。

## 三、调用入口（llm.py）

### 1. 普通 SQL 生成（`init_messages`）

```
1. 若有 generate_sql_logs：
   - 取 latest_log，从 messages 取 history_question
   - 先 LLM 增强，否则规则增强
   - 用 enhanced_question 覆盖 chat_question.question

2. 表选择规则、jq_zbval 规则等注入 custom_prompt

3. 若有 generate_sql_logs：
   - analyze_context_needs(original_question, generate_sql_logs)
   - 若 needs_any_context：extract_context → build_context_prompt
   - 将 context 作为 HumanMessage 追加到 sql_message
```

### 2. 快速模板匹配（`generate_straight_sql_info`）

- 同样会做问题增强和上下文分析
- 流程与普通 SQL 生成类似，但走的是 straight 模板匹配

## 四、典型示例

### 示例 1：时间追问

```
轮1：2025年海南省法人户数是多少？
→ 生成 SQL：create_date LIKE '2025%', name_1='海南省'

轮2：2024年的呢？
→ is_time_follow_up = True
→ 规则增强：2024年海南省法人户数是多少？
→ 提取 time_range（若历史 SQL 含 BETWEEN 等）
→ 生成 SQL：create_date LIKE '2024%', name_1='海南省'
```

**潜在问题**：若历史 SQL 为 `create_date LIKE '2025%'`，`extract_time_range` 无法解析，`time_range` 为空，模型可能无法正确延续时间。

---

### 示例 2：地区追问

```
轮1：2025年海南省法人户数是多少？
轮2：广东的呢？
→ is_region_follow_up = True
→ 规则增强：2025年广东省法人户数是多少？
```

---

### 示例 3：指代词 + 实体引用

```
轮1：2025年海南省注册的法人有哪些？（返回公司列表）
轮2：这些公司的营业收入分别是多少？
→ 含「这些」→ needs_entity_ref
→ 从 record.data 提取公司列表 → entity-ref type="company"
→ context 注入：<entity-ref type="company">公司A, 公司B, ...</entity-ref>
→ 模型生成 SQL：WHERE company IN ('公司A', '公司B', ...)
```

**潜在问题**：`extract_companies` 依赖字段名匹配（company_name、公司名称等），若实际字段名不同，可能提取失败。

---

### 示例 4：指标追问

```
轮1：2025年海南省法人户数是多少？
轮2：营业收入呢？
→ is_metric_follow_up = True
→ 规则增强：2025年海南省营业收入是多少？
→ 但历史问题为「法人户数」，替换后语义可能变为「营业收入」而非「法人户数的营业收入」
```

**潜在问题**：指标追问的替换逻辑较简单，可能产生语义偏差。

---

### 示例 5：超过 25 字的追问

```
轮1：2025年海南省法人户数是多少？
轮2：那2024年海南省的法人户数是多少呢？
→ 长度 > 25 → 不视为追问
→ 不触发规则增强
→ 若不含指代词，可能不触发 context 提取
→ 模型需独立理解完整问题
```

## 五、已知问题与优化方向

### 1. 时间范围提取不完整

- **问题**：`extract_time_range` 不支持 `create_date LIKE 'YYYY-MM%'`
- **影响**：法人户数等场景下，时间追问无法延续正确时间范围
- **建议**：扩展正则，支持 `LIKE 'YYYYMM%'` 或 `LIKE 'YYYY-MM%'`

### 2. 追问长度限制过严

- **问题**：`_FOLLOW_UP_MAX_LEN = 25`，稍长追问会被视为完整问句
- **影响**：「那2024年海南省的法人户数是多少呢？」等无法触发规则增强
- **建议**：适当放宽或改为按句式模式匹配，而非长度

### 3. 仅依赖最近一轮

- **问题**：`latest_log = generate_sql_logs[-1]`，只取最近一轮
- **影响**：若用户指「上一轮」或「刚才那个」但中间插有其他轮，可能取错上下文
- **建议**：支持多轮回溯或显式轮次引用

### 4. 实体提取字段名硬编码

- **问题**：`company_field_names` 等写死，与实际 schema 可能不一致
- **影响**：公司列表等实体提取失败
- **建议**：结合 schema 或术语表动态识别字段

### 5. 指标追问替换逻辑

- **问题**：`enhance_question_for_metric_follow_up` 用简单替换，可能改变原意
- **建议**：结合历史 SQL 的指标字段，做更精确的替换或补充

### 6. 上下文需求分析偏宽

- **问题**：`len(history_logs) > 0` 时默认 `needs_intent_context = True`
- **影响**：即使用户问的是全新问题，也会注入上下文，可能干扰模型
- **建议**：增加「是否追问/延续」判断，仅在必要时注入 context
