# 法人户数 / create_date 时间逻辑分析

## 问题背景

数据库数据更新频率比实际时间慢约一个月。例如当前为 2026 年 2 月，库中最新数据只到 2026 年 1 月。用户问「海南省 2026 年 2 月...」时，SQL 会生成 `create_date LIKE '2026-02%'`，导致查询结果为空。

---

## 相关代码位置

### 1. 核心逻辑：`_get_effective_current_time()`

**文件**：`backend/apps/chat/task/llm.py` 第 246-296 行

**作用**：当问题涉及法人户数且**未指定时间**时，从 `dws_cqs_enterprise_query_view_full` 取 `MAX(create_date)` 作为 `current_time`，供 prompt 使用。

**当前逻辑（表驱动 + 时间指定）**：
```python
# 若 schema 中不含 cqs 表，使用系统时间
if 'dws_cqs' not in schema:
    return default_time

# 问题中已包含明确时间则用系统时间
time_keywords = ['时间', '日期', '月份', '年份', '年', '月', '日', '去年', '今年', '前年']
if any(kw in question for kw in time_keywords):
    return default_time

# cqs 表 + 未指定时间 → 查 MAX(create_date)
```

**逻辑说明**：须同时满足 (1) schema 含 dws_cqs 表，(2) 问题未明确指定时间，才从数据源取最新 create_date；否则使用系统时间。

### 3. 模板中的 current_time 使用

**文件**：`backend/template.yaml`

- **第 302-303 行**（Instruction）：
  > 当用户问题涉及「法人户数」「集团法人户数」且**未在问题中指定具体时间**时，`<current-time>` 表示业务数据当前可查询的最新时间，create_date 必须使用其年月。

- **第 328-329 行**（Rules）：
  > **法人户数时间**：当用户问题涉及法人户数且**未在问题中指定具体时间**时，create_date 必须与 `<current-time>` 的年月一致。

- **第 554-558 行**（user 模板）：
  ```yaml
  <background-infos>
    <current-time>{current_time}</current-time>
  </background-infos>
  ```

**问题**：模板强调「未指定时间」才用 current_time，但 `_get_effective_current_time` 在用户指定时间时直接返回系统时间，两者配合后，指定时间场景下无法利用「库中最新时间」。

---

### 4. 表选择规则（年报表/月报表）

**文件**：`backend/apps/chat/utils/table_selection_rule.py`

- 使用 `current_time` 判断「当前年份/月份」
- 若用户问的是未来月份（如 2026 年 2 月），可能返回 `status: "no_data"`
- 该逻辑主要针对 `dws_cgn_jq_zbval_month` 等指标表，与法人户数视图 `dws_cqs_enterprise_query_view_full` 是不同场景

---

### 5. 时间范围提取（追问场景）

**文件**：`backend/apps/chat/context/extractors.py` 第 74-148 行

`extract_time_range()` 从历史 SQL 中提取时间，支持：
- `BETWEEN 'YYYYMM' AND 'YYYYMM'`
- `BETWEEN 'YYYYMMDD' AND 'YYYYMMDD'`
- `= 'YYYYMM'` / `= 'YYYYMMDD'`
- `IN ('YYYYMM', ...)`

**不支持**：`create_date LIKE '2026-02%'` 这类 LIKE 模式，追问时可能无法正确延续时间范围。

---

## 根因总结

1. **`_get_effective_current_time`**：一旦问题包含「年」「月」等时间词，就返回系统时间，不再使用库中 `MAX(create_date)`。
2. **模板**：只约束「未指定时间」场景，未处理「用户指定时间晚于库中最新时间」的情况。
3. **时间提取**：`extract_time_range` 不支持 `create_date LIKE 'YYYY-MM%'`，追问时可能拿不到正确时间。

---

## 优化方向建议

### 方案 A：放宽「指定时间」时的逻辑

- 问题涉及法人户数 / `dws_cqs_enterprise_query_view_full` 时，**始终**查询 `MAX(create_date)` 作为 `data_latest_time`。
- 若用户指定时间（如 2026 年 2 月）晚于 `data_latest_time`（如 2026-01），则：
  - 将 `current_time` 设为 `data_latest_time`，或
  - 在 prompt 中显式说明：「数据最新到 YYYY-MM，若用户问的时间晚于此时，create_date 必须使用 YYYY-MM」。

### 方案 B：在 prompt 中同时提供两个时间

- `current_time`：系统时间（用户理解上的「当前」）。
- `data_latest_time`：库中 `MAX(create_date)`。
- 规则：create_date 必须使用 `min(用户指定时间, data_latest_time)` 的年月。

### 方案 C：SQL 执行后重试

- 若 SQL 返回空结果，且涉及 `create_date` 且时间在「未来」：
  - 自动将时间回退一个月重试；
  - 或根据 `MAX(create_date)` 重写时间条件后再执行。

### 方案 D：扩展 `extract_time_range`

- 增加对 `create_date LIKE 'YYYY-MM%'` 的解析，使追问时能正确延续时间范围。

---

## 建议优先顺序

1. **方案 A / B**：从 prompt 和 `_get_effective_current_time` 入手，让「指定时间」场景也能使用库中最新时间，改动集中、影响面可控。
2. **方案 D**：补齐 `extract_time_range`，改善追问场景。
3. **方案 C**：作为兜底，在空结果时做时间回退或重试，实现成本相对较高。
